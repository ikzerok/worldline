# 当前正文草稿的隔离试演

工具 0.32 提供独立的当前正文草稿试演。普通试玩继续只消费已应用的工程稿；
已应用但未保存的修改仍参与普通试玩。新模式须由作者明确选择和核对范围，
不会应用、保存、清除或重建 WritingBuffer，也不会替换既有普通试玩会话。

## 快照与输入

`DraftRehearsalRequest` 绑定 `schema_version: 1`、完整 `content_baseline`，并携带
`drafts`、`excluded_inputs`、`composing`。每个 `DraftRehearsalInput` 包含工作区
相对 `.wl` 路径、完整 `original_source`、完整 `source` 和 `generation`。
`original_source` 必须仍等于 Project 当前源文；草稿基线必须等于完整内容基线。
同一文件只允许一项，完全相同的重复项也拒绝。`drafts` 数组次序不构成文件身份；
编译和动作时重验均按真实路径对应完整原文、新文及代次，不把正常重排判断为过期。
多个章节共享同一 WritingBuffer，
不会按章节重复覆盖。路径别名、非活动源、删除源和工作区外文件均拒绝。

Rust 的 `DraftRehearsalRequest::from_writing_buffers` 从现有缓冲捕获这些字段；
机器接口消费同一 DTO。反序列化不是写入授权。`excluded_inputs` 的 `kind` 与
`source` 仅解释宿主未提交的表单，不送入编译器；宿主负责列全实际未提交输入。
已登记书稿的排序和正文引用不成为执行入口。待新建事件、表单、导入候选、
未插入的保留正文和 IME 组合文本不隐式混入；有尚未完成的正文组合/保留输入时
拒绝建立声称“当前正文”的快照，输入完整保留。

JSON 草稿 `generation` 与机器调用 `seed` 必须不大于 9007199254740991，超出时明确
拒绝；运行指纹以十进制字符串传输，现有状态检查 stamp 沿用其精确编码。

请求最多 256 份草稿、草稿前后源文合计 16 MiB、256 项排除说明（每项文本合计
4096 字节），完整活动源码最多 4096 文件、64 MiB。超限失败，不截断或选择部分稿。
至少须有一份真正改变的活动源草稿；未改变的打开缓冲不计入覆盖。
未知工作区能力、未解决保存事务、完整保存基线或外部源清单变化、无效源文均失败。
不因纯运行要求文件的 OS 写权限，也不改只读文件；未知能力仍遵守现有工作区保护。

core 调用既有 `compile_writing_drafts`，并核对编译来源与预计完整活动源集合逐字节
一致。返回的 `DraftRehearsalSnapshot` 私有持有真实 CompileResult、完整请求、工作区
身份与刷新代次；只读 `scope()` 明确列出草稿覆盖/已应用输入、草稿代次、源文字节数、
执行指纹、入口和全部排除项。没有第二种解析器，也不从任意节点绕过初始化。

## 真实运行与来源

runtime `DraftRehearsal` 只从此快照建立新的 `OwnedStory`，使用明确 seed 和实际
入口。选择、once、随机、片段、错误、状态检查、条件求值证据、步数/时间预算和
取消与普通运行使用相同状态机。暂停/继续只作用于本次试演。重复开始明确新建会话，
不恢复或猜测旧 choice 意图，不自动续接原路线。

真实推进、初始化或状态/证据预算失败后，当前 `outcome` 为空并报告停止原因，
不能沿用上一次“等待选择”或成功结束的结果。已收到的历史正文仍可查看。
参数、外来会话或未知 choice 请求的拒绝不改变真实 Story；若它仍等待选择，
该等待状态和实际选择继续有效。既有 RunError 文本与来源行号语义不变。

快照不会后台热替换。作者编辑、应用、外部刷新、工作区/语言变化后，既有输出仍是
旧快照的真实证据；界面明确标旧，可继续观察冻结快照，但不得当作当前作者位置。
界面用宿主版本和缓冲代次作无 IO 的失效提示，不在每个空闲帧克隆或散列完整工程。
执行当前草稿选择或来源跳转前，重新核对完整内容、缓冲集合、源文和代次；原生来源
跳转还检查完整工作区保存基线与磁盘身份。WASM 只验证已导入快照；重新导入使旧
来源失效，不声称持续观察宿主磁盘。

来源来自试演自己的 CompileResult 和 Story。条件/状态声明通过现有 core 来源解析器
定位；精度仍是声明头，不伪称子表达式范围。返回初始草稿恢复同一文件、章节、模式、
选区和滚动；仅在完全一致时恢复旧位置。失效时保留只读证据和作者全部输入，拒绝
按相似名称跳到别处。回源不得自动应用、保存、撤销或清空草稿。

## 正式记录边界

本模式不提供保存游戏、检查点、持久 trace 导入/导出或路线报告保存入口，不把缺少
草稿来源合同的记录塞进已有正式通道。既有普通试玩、保存格式、strict replay 和
checkpoint fingerprint 检查保持不变。首个完整作者循环为：

1. 写未应用正文，明确核对并试演
2. 查看实际输出、选择、状态和条件，返回同一草稿修改
3. 明确重新试演，旧 Story 不热替换
4. 作者另行明确应用正文
5. 从新的已应用稿开始普通试玩，再录制正式路径

## Rust、CLI 与 RPC

`Project::compile_draft_rehearsal(&request)` 是唯一建立快照的 core 入口。
`DraftRehearsal::new(snapshot, seed)`、`continue_bounded`、`choose_id` /
`choose_presentation` 与 `inspect_state` 提供会话等价语义；仅有界推进改变该独立会话。
机器调用使用同一请求/适配器，明确传入本次 choice ID，不自动采用任何旧保存路线。
请求结构、未知字段或非法参数是协议错误；编译、基线、来源或故事执行失败返回
业务 `ok:false` 和中文原因。所有失败不得改变 Project、磁盘、撤销栈或普通会话。

## 编辑器后台会话合同

首次构建在原生专用线程 / 浏览器同源专用 Worker 中执行，主线程不重新编译。
Prepare 只编译并保有快照；范围确认后 Start 建立一份 OwnedStory。Continue、
Choose（实际当前 choice ID）、Inspect、EvidenceSource、DeclarationSource 都访问
这同一份会话，不用重放既往选择模拟继续。Program/Analysis 不跨 JSON 传输。

准备确认层打开时，作者全局撤销、保存、打开工程和普通试玩快捷键不得穿透。
非 IME Escape 仅取消本次准备，底下新文件名、搜索和正文输入完整保留；本帧
取消后同一批快捷键也不得触发底层动作。IME Enabled/Preedit/候选键/Commit/
Disabled 仍交给原接收控件，组合及完成帧不把 Escape/Enter 当作确认或取消。

内部协议固定版本 1，session_id/request_id 使用字符串；同时最多一个在途请求。
输入 JSON 最多 32 MiB，结果最多 8 MiB，工程快照遵守 4096 文件/64 MiB 源码及
现有完整快照文件边界。未知字段、不同会话、乱序或过期结果拒绝。运行单次推进
有明确步数/时间额度；查看状态和来源不推进运行。新试演另建 Worker，确认前旧
试演与普通试玩保留；取消准备释放新 Worker，关闭/换工程释放全部本模式资源。

原生编译器暂不能在内部抢占：取消使返回结果失效，后台编译结束后释放，不阻塞
作者继续输入。浏览器取消通过终止专用 Worker 释放。运行中强制关闭只保留已接收
的证据，明确不声称捕获了未返回的部分状态。暂停后的继续仍用原快照，不热替换。

本模式累计真实文本输出沿用逐语句预算门，最多 1 MiB / 32768 条输出；真实状态
借用预检最多 1 MiB / 16384 记录，条件/选择证据各最多 1 MiB。完整机器响应另有
8 MiB 上限，完整请求 JSON 最多 32 MiB。这些是不同预算，不能用响应上限冒充会话
输出上限。超限当场停止，不先积累无界状态 JSON；`outputs_complete:false` 明确说明
未返回的实际输出不完整。预算失败不影响普通试玩，也不重放已执行语句。

原生同一进程最多一个不可抢占的试演编译。取消后若旧编译尚未退出，新准备请求
在界面等待许可，不创建更多线程或Project副本；旧任务结束/报错后释放许可。
同一作者快照仍旧时才启动等待中的请求；取消、改稿或换工程丢弃它。

命令为 `wl draft-rehearsal PATH (--request-json JSON | --request FILE) [--json]`。
RPC为 `project.draft_rehearsal {project_id, request}`，共享runtime请求/结果与验证。
业务响应外壳 `{ok, applied:false, saved:false, result}` 保留 `result.ok:false` 领域
失败；协议参数错误为 `-32602`。RPC ID编码最多2048字节。请求JSON上限32MiB，
runtime结果上限8MiB，CLI/RPC整行另预留4096字节外壳；Worker消息继续遵守独立
内部协议预算，不能把这些不同边界混为一个限制。
