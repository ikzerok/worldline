# 实施方案：从当前代码到内容、地图与关联工作台

版本0.2，待评审（0.2修订：WP-04 重写为矢量画布，基础线面前移 M1，WP-14 收缩为展示预设与专题）。本文给出可拆成PR的工作包、依赖和证据要求；没有创建GitHub Issue或PR，没有修改远程仓库，也没有执行这里列出的Rust命令。

## 1. 总体选择

先做地图展示的纵向切片，复用现有TargetRef和tag/人物资料；不等待通用实体或复杂关系系统。之后再加入entity和独立关系，最后补齐内容模板、叙事关联、线面与文件协作。

持久化、撤销和冲突检测不能当最后的“收尾”。地图JSON必须从第一阶段进入Project生命周期；UI直接写文件的临时实现不得作为可发布方案。

复杂度S/M/L只是相对工作量和风险提示，不是工期估计。建议职责：核心维护者负责语言、契约与存储；界面维护者负责交互、渲染与平台；共同评审负责样例与验收。单人也可依顺序执行。

## 3. 第一阶段关键路径

```text
WP-00 → WP-01 → WP-02 → WP-03 ─┬→ WP-05 ─┐
              └→ WP-04 ───────┘         ├→ WP-07
                       WP-02/03 → WP-06 ┘
```

先用已有tag词条/人物挂到地图，因此通用entity、关系语法不是M1阻塞项。M1画布为矢量原生（0.2修订决策）：标记/线/面是原生图元，栅格图为可放置图层，坐标属于地图文档自身坐标系。WP-04可以用本包格式样例验证相机、图元和栅格图层；正式界面接入必须等core地图查询API，不允许把原型JSON解析复制成第二真源。

## 4. 每个PR应该怎样提交

一个PR只改变清楚的契约或交互切片，同时包含测试和规范；不要把工具链升级、新地图、全新文本语法与云协作一起提交。

核心PR先合并DTO/读取与测试，再合并写入；编辑器可在兼容SHA上开发。跨仓库未合并时CI采用明确的测试SHA，不用浮动main“碰运气”。地图格式或关系格式有字段变化时同时更新Schema、示例和未知字段往返测试。

PR描述至少包括：需求ID、现有行为、修改行为、不变量影响、测试、迁移/回退方式、实际验证平台。模板见`../tools/PR_TEMPLATE.md`。

## 5. 应先处理的当前代码点

### Project文件管理

`refresh`只读取wl，`sources`返回全部documents，`restore/mark_saved/is_dirty`只处理现有文档。[R04] 新元数据必须加入统一生命周期，而sources保持只给编译器源码。不要把地图JSON直接塞入旧sources。

### 结构编辑验证

原Project::edit拒绝任何编译错误。[R06] 保留旧行为，新增Presentation命令单独检查。需要测试“一个章节未写完，但另一张合法地图仍可移动标记”的情况。

### 纯内容工程

打包路径目前会拒绝无事件。[R04] 移除内容包的这一条件；启动Story仍校验入口。不要偷偷给纯内容项目生成一个END事件。

### 运行失效边界

检查worldedit全局version、快照重建和PlayState.version用途。[R07] 地图变动只提高presentation_generation；不改变旧Program fingerprint，不重置试玩会话。

### 图像并非已有地图支持

当前media主要打开外部文件。[R08] 应新增独立渲染管线和受限纹理缓存，不能在每一帧从磁盘读取并解码原图。

### 跨仓库CI

现有CI checkout worldline未指定ref。[R12] 建议新增`worldline-compatibility.json`记录仓库和SHA，由CI读取后checkout。同级path依赖保留；文件声明不是自动保证，CI必须实际用该SHA构建。[E07]

## 7. 旧工程兼容与回退

无新清单旧工程按原逻辑读取；M1不要求新语言。启动地图功能需明确创建新元数据；1.10实体和关系需明确升级language_version并保留改动前副本。

未知新格式只读；不能承诺旧0.2.0能正确识别或安全保存新JSON。回退编辑器前保留完整工程副本；旧工具仅用于未升级的工程。原runtime存档兼容维持已声明边界，旧关系提升等转换是否等价必须另有测试。
